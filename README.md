# Executive Dashboard: эффективность торговой команды

Управленческий дашборд по KPI, премированию и загрузке торговой команды.
Собирается из двух Excel-выгрузок: факт по KPI за август 2026 и план-календарь
активностей на сентябрь 2026.

Проект состоит из двух частей: ETL, который превращает Excel в хранилище SQLite
со звёздной схемой, и дашборда на Next.js, который читает это хранилище.

## Запуск

```bash
npm install
npm run dev
```

Дашборд откроется на [http://localhost:4317](http://localhost:4317).
`npm run dev` сначала запускает ETL, поэтому хранилище всегда соответствует
текущим файлам в `uploads/`.

Хранилище — локальный файл `data/warehouse.db`, который не коммитится и
пересобирается из источников. Для свободных вопросов в диалоге можно
подключить нейросеть: скопируйте `.env.example` в `.env.local` и задайте
`OPENAI_API_KEY` (подходит любой OpenAI-compatible endpoint через
`OPENAI_BASE_URL`). Без ключа диалог отвечает правилами SQL и логическим
fallback по сводке KPI.

## Команды

| Команда | Что делает |
| --- | --- |
| `npm run dev` | ETL, затем дев-сервер на порту 4317 |
| `npm run etl` | Пересобрать `data/warehouse.db` из файлов в `uploads/` |
| `npm run verify` | Сверить хранилище с источником и проверить модель премирования |
| `npm run build` | ETL и продакшен-сборка |
| `npm run lint` | ESLint |

## Что показывает дашборд

Все показатели эффективности считаются по исполнителям (TSM, JTSM, KPP
Activator). Строки BDM и RKAM в источнике — свёртка команды целиком, поэтому в
средние они не входят, иначе одни и те же визиты считались бы дважды.

- **Ключевые показатели** — средний балл KPI, доля выполнивших норму, доля
  оставшихся без премии и итоговая ставка премии с разложением на базовую ставку
  и потери от штрафов.
- **Распределение по баллам** — сколько сотрудников попало в каждую зону
  премирования.
- **Зона быстрого выигрыша** — сотрудники у порога 100 баллов, на котором ставка
  премии скачком удваивается. Для каждого показано, сколько баллов не хватает и
  какой прирост ставки это даёт.
- **Выполнение по метрикам** — каждая метрика сравнивается со своей целью: часть
  KPI имеет цель ниже 100% по дизайну схемы (например, у POSM на кассе цель —
  50% исполнения).
- **Регионы** — средний балл с переключением между отстающими и лидерами.
- **Штрафы по контрольным турам** — распределение по размеру штрафа и доля
  бюджета премий, которую съедают удержания.
- **Лидеры и отстающие территории** — по 10 позиций с деталями расчёта премии.
- **Потери полевого времени** — план на сентябрь по типам активностей. Фильтры к
  этому блоку не применяются: календарь относится к другому периоду и другому
  составу команды.
- **Качество данных** — замечания, найденные при загрузке источников.

Фильтры по региону, должности и руководителю (IBM) живут в URL, поэтому
конкретный срез можно сохранить в закладки или отправить коллеге.

### Диалог «Спросить данные»

В шапке и в правом нижнем углу — кнопка, которая открывает диалог с вопросами
на естественном языке. Примеры:

- «Кого дотянуть до 100 баллов для наибольшего эффекта?»
- «У кого из сотрудников лучший KPI?»
- «Выдай топ-5 регионов по среднему баллу»
- «Сравни менеджеров IBM по KPI»

Как отвечает диалог:

1. Если задан `OPENAI_API_KEY` — вопрос уходит в нейросеть вместе с компактной
   сводкой из SQLite (KPI, регионы, IBM, зона порога 100, штрафы, календарь).
   Модель опирается на эти цифры; если точных данных нет, даёт помеченный
   логический вывод по правилам премирования.
2. Без ключа или при сбое API — проверенные SQL-правила по ключевым словам.
3. Если правило не сработало — логический fallback (часто зона быстрого
   выигрыша у порога 100 баллов).

API: `GET /api/ask` (подсказки + статус LLM), `POST /api/ask` с телом
`{ "question": "..." }`.

## Структура

```
scripts/
  etl.ts                 Excel -> SQLite
  verify.ts              Сверка агрегатов с источником
  verify_incentive.ts    Проверка модели премирования на всех строках
src/
  lib/
    schema.sql           Схема хранилища
    db.ts                Доступ к SQLite только для чтения
    queries.ts           Аналитические запросы дашборда
    ask.ts               Правила ответов на вопросы
    ask-context.ts       Сводка хранилища для LLM
    ask-llm.ts           Клиент OpenAI-compatible Chat Completions
    incentive.ts         Модель премирования
    format.ts            Форматирование чисел и склонения
  components/            Компоненты дашборда и графики
  app/page.tsx           Executive dashboard
  app/api/ask/           API диалога
uploads/                 Исходные Excel-файлы
docs/DATA.md             Справочник по данным и расчётным правилам
.env.example             Шаблон ключа нейросети
```

## Как добавить новый период

Положите новую выгрузку в `uploads/` и запустите `npm run etl`. ETL находит
файлы по префиксу имени (`EVA_Final_08`, `CA_Sep_26`) — для другого месяца
обновите константы периодов и префиксы в начале `scripts/etl.ts`.

## Важное о данных

Подробный разбор — в [`docs/DATA.md`](docs/DATA.md). Сравнение источников и ответ
на вопрос «можно ли собрать EVA из CA» — в [`docs/CA_VS_EVA.md`](docs/CA_VS_EVA.md).

Коротко о том, что влияет на трактовку цифр:

- **Период календаря определён по содержимому.** Лист подписан «СА June'26», но
  распределение выходных соответствует сентябрю 2026 — название осталось от
  июньского шаблона.
- **Абсолютных сумм премий в дашборде нет.** В файлах отсутствуют оклады, поэтому
  премия выражается в ставке (% от оклада) и в процентных пунктах. Чтобы считать
  деньги, нужна выгрузка по окладам.
- **Сквозное сравнение план-факт по сотруднику некорректно.** Состав территорий
  между августом и сентябрём различается: 9 территорий есть только в EVA, 10 —
  только в CA.
- **ФИО сотрудников недоступны.** В рейтингах они заменены ошибкой `#REF!`,
  поэтому идентификация идёт по коду территории.
