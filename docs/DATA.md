# Справочник по данным

Описание источников, модели хранилища и проверенных расчётных правил. Все
утверждения здесь либо прочитаны прямо из файлов, либо проверены скриптами
(`npm run verify`).

## Источники

### `uploads/EVA_Final_08_*.xlsx` — факт по KPI и премиям

Период — **август 2026** (из названия файла и листа «Rating 08»).

**Лист `Russia_Bonus KPIs`.** Шапка занимает строки 4–6 (трёхуровневая, с
объединёнными ячейками), данные — строки 7–188, итого 182 записи. Одна запись =
одна территория.

| Столбцы | Содержание |
| --- | --- |
| A | IBM — руководитель направления. Заполнен только в первой строке блока (объединённая ячейка), в ETL протягивается вниз |
| B, C, D | Регион, код территории, должность |
| E, F | Схема KPI (`30% TOP-10 +70% KPP` и др.) и группа KPI |
| G | Summary Score — доля выполнения, 0..2 |
| H–K | Индивидуальная задача: порог 100%, порог 200%, факт, выполнение |
| L–N | TOP-10: порог 100%, порог 200%, выполнение |
| O, P | Выполнение KPP и обязательной задачи |
| Q–U | Call rate: рабочие дни, визиты, план, факт, выполнение |
| V–Y | Покрытие маршрута: план, факт, выполнение, не посещено |
| Z–AB | POSM на кассе: план, факт, выполнение |
| AC–AE | POSM на оборудовании |
| AF–AH | Контрактные SKU |
| AI–AK | Неконтрактные SKU |
| AL–AN | SKU по цели |
| AO, AP | Соответствие дистрибуции и H/S |
| AQ–AS | Качество: проверено точек, точек с ошибками, зачёт по KPI |
| AT–AW | Итоговый балл, ставка премии, штраф по турам, итоговая ставка |

**Лист `Rating 08`.** Три независимых блока рейтинга (TSM, BDM, RKAM) и шкала
премирования в столбцах V–AJ. Столбцы с ФИО содержат `#REF!`, поэтому
сотрудники идентифицируются по коду территории.

### `uploads/CA_Sep_26_*.xlsx` — план-календарь активностей

Период — **сентябрь 2026**. Лист подписан «СА June'26», но выходные в данных
приходятся на 5–6, 12–13, 19–20 и 26–27 числа, что соответствует календарю
сентября 2026 года (1 сентября 2026 — вторник); в июне 2026 выходные выпадают на
другие даты. Название листа осталось от июньского шаблона, поэтому ETL
определяет период по содержимому, а не по подписи.

Строка 2 — шапка: `BDM`, `Territory name`, `Region`, `Position`, далее номера
дней. Каждый день занимает два столбца (активность и часы), день 1 начинается со
столбца E. Данные — строки 4–186, 30 дней.

Лист `Sheet2` — справочник: 11 типов активностей, варианты длительности
(2/4/6/8 ч) и статусы согласования.

В календаре отмечается **только то, что отвлекает от работы в полях**. Пустая
ячейка в рабочий день означает обычную полевую работу, поэтому заполненные
ячейки трактуются как потери полевого времени, а не как весь график.

## Иерархия

```
IBM (8 человек, только в EVA)
└── BDM / RKAM — код территории оканчивается на 00, строка-свёртка команды
    └── TSM / JTSM / KPP Activator — код оканчивается на 01..09, исполнители
```

Строки BDM и RKAM содержат суммы по своей команде (визиты, точки, SKU), поэтому
**в средние по эффективности они не включаются** — иначе одни и те же визиты
посчитались бы дважды. В хранилище это флаг `dim_territory.is_rollup`.

Состав: 129 TSM, 12 JTSM, 7 KPP Activator (исполнители), 29 BDM и 5 RKAM
(свёртки). Балл рассчитан у 141 исполнителя из 148 — у остальных схема `No KPI`.

## Проверенные расчётные правила

Три правила восстановлены из файла и проверены на всех строках
(`scripts/verify.ts`, `scripts/verify_incentive.ts` — 0 расхождений).

**1. Итоговый балл.**

```
final_kpi_score = summary_score * 100          # шкала 0..200
```

**2. Summary Score учитывает обязательную задачу как множитель.**

```
summary_score = (доли TOP-10 и KPP согласно type_kpi) * mandatory_achieve
```

Например, территория 1160102: схема `50% TOP-10 +50% KPP`, TOP-10 = 1,368,
KPP = 1,8, обязательная задача = 0,5. Смесь даёт 1,584, после умножения на
0,5 — 0,792, что совпадает с файлом. Невыполненная обязательная задача
пропорционально срезает весь балл.

**3. Ставка премии зависит от балла с разрывом на 100 баллах.**

```
балл < 80        -> 0
80 <= балл < 90  -> 5,0% + (балл - 80) * 0,25%     # 2,5% на 10 баллов
90 <= балл < 100 -> 7,5% + (балл - 90) * 0,25%     # до 9,9% на 99,6 балла
балл >= 100      -> балл * 0,2%                    # 20% на 100, 40% на 200

final_incentive_rate = incentive_rate * (1 - tour_penalty)
```

Оба наклона совпадают с подписями в шапке листа «Rating 08» — «2.5% per 10
Point» и «2.0% per 10 Point». Реализация — `src/lib/incentive.ts`.

Практический вывод: на 100 баллах ставка скачком растёт с ~9,9% до 20%.
Сотрудник, не дотянувший один балл, теряет половину премии — поэтому дашборд
выделяет группу у этого порога отдельным блоком.

## Что из источника сознательно не трактуется

Столбец AS (`POS with Mistakes` → `Achieve, %`) содержит зачёт по KPI, правило
которого в файле противоречиво: при уровне ошибок 5,6% встречается зачёт 0,05, а
при 12,2% — 0. Поэтому дашборд показывает фактический уровень ошибок
(`pos_with_mistakes / covered_pos`), который считается однозначно, а исходный
зачёт сохраняется в хранилище без интерпретации.

## Модель хранилища

Звёздная схема в SQLite, полная спецификация — `src/lib/schema.sql`.

| Таблица | Назначение |
| --- | --- |
| `dim_period` | Периоды с указанием файла-источника |
| `dim_region` | Нормализованные регионы и их исходные написания |
| `dim_ibm` | Руководители направлений |
| `dim_territory` | Территории, должность, флаг свёртки, связи BDM и IBM |
| `dim_activity_type` | Типы активностей, категории, признак потери времени |
| `dim_incentive_scale` | Шкала премирования из источника |
| `fact_kpi` | Факт по KPI и премиям, зерно: территория + период |
| `fact_rating` | Рейтинги по трём блокам должностей |
| `fact_activity` | Календарь, зерно: территория + период + день + активность |
| `data_quality_issue` | Замечания, выявленные при загрузке |
| `etl_run` | Журнал загрузок |

## Качество данных

ETL не маскирует проблемы источника, а записывает их в `data_quality_issue`,
откуда они выводятся на дашборд.

**Исправляется автоматически.** Регионы, отличающиеся только регистром или
разделителем (`Saint Petersburg` / `Saint-Petersburg`, `Rostov-on-Don` /
`Rostov-on-don`), объединяются; исходные написания сохраняются в
`dim_region.variants`.

**Выносится на решение владельца данных.** Пары названий, где одно получается из
другого выпадением 1–2 букв при длине не меньше 8 символов, помечаются как
вероятная опечатка, но не объединяются: так найдена пара `Novorossiysk` /
`Novorosysk`. Правило намеренно узкое — города с разными буквами (`Tomsk` /
`Omsk`, `Ryazan` / `Kazan`) под него не попадают.

**Прочие известные ограничения.**

- В рейтингах нет ФИО (`#REF!`), сотрудники идентифицируются по коду территории.
- Состав территорий между файлами различается: 9 есть только в EVA, 10 — только
  в CA. Штат менялся между августом и сентябрём, поэтому сквозное сравнение
  «план загрузки против факта KPI» по одному человеку некорректно.
- Абсолютные суммы премий посчитать нельзя: в файлах нет окладов. Дашборд
  оперирует ставкой в процентах от оклада и разницей в процентных пунктах.
- Территория 1120301 имеет Summary Score = 0 при выполненных KPP и обязательной
  задаче. Похоже на ручное обнуление в источнике; данные загружаются как есть.
